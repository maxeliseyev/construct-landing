Криптография просто

Интерактивная демонстрация на маленьких числах (p = 71, G = 2)

Приватный и публичный ключ — в чем разница?

Представьте, что у нас есть особый калькулятор, который умеет делать только одну операцию: возводить число в степень и брать остаток от деления на 71 (простое число).

Правила игры:

  • Базовая точка G = 2
  • Приватный ключ — число, которое знаете только вы
  • Публичный ключ = G^приватный mod 71
Алиса берет приватный ключ 12
→ вычисляет 2^12 = 4096
→ 4096 ÷ 71 = 57 целых, остаток 49
→ Публичный ключ Алисы = 49

Боб берет приватный ключ 56
→ 2^56 ÷ 71 = остаток 25
→ Публичный ключ Боба = 25

NB: из 49 невозможно вычислить 12, не перебрав все варианты. Для маленьких чисел это легко, но в реальности числа огромные (2²⁵⁶).

Публичный ключ = 2^a mod 71

Боб


25

Публичный ключ = 2^b mod 71

Как договориться об общем секрете, не встречаясь?

Алиса и Боб хотят получить одинаковое число, чтобы шифровать им сообщения, но так, чтобы никто другой его не узнал.

Протокол Диффи-Хеллмана (упрощенно): 

Шаг 1: Алиса → Боб: публичный ключ Алисы (49)
Шаг 2: Боб → Алиса: публичный ключ Боба (25)

Шаг 3: Алиса вычисляет: 25^12 mod 71 = ???
Шаг 4: Боб вычисляет: 49^56 mod 71 = ???

Магия: результаты одинаковы!

Общий секрет S = 2^(a×b) mod 71. Злоумышленник видит только 49 и 25 и не знает a и b.

Алиса → Боб: 49

Боб → Алиса: 25

Алиса вычисляет: 25^12 mod 71 = 57

Боб вычисляет: 49^56 mod 71 = 57

Общий секрет: 57

Мини-чат: как текст превращается в шифротекст

Теперь возьмём общий секрет S = 57 и используем его как учебный симметричный ключ для чата.

Чтобы даже русские буквы помещались в нашу маленькую математику по модулю 71, мы сначала переводим сообщение в UTF-8 байты, потом разбиваем каждый байт на две шестнадцатеричные цифры (0..f), и уже эти маленькие числа шифруем по модулю 71.

Это именно учебная схема, а не настоящий протокол Signal: она нужна, чтобы наглядно показать путь текст → числа → hex → шифрование.

А если злоумышленник подменит ключи?

Атака “человек посередине” (MITM) выглядит так: злоумышленник перехватывает обмен и подставляет свои ключи. 

Алиса → Ева: 49
Ева → Боб: 33 (свой ключ)
Боб → Ева: 25
Ева → Алиса: 44 (свой другой ключ)

Теперь:
- Алиса думает, что общается с Бобом, но на самом деле с Евой
- Боб думает, что общается с Алисой, но на самом деле с Евой

Решение: нужна аутентификация. В Signal для этого используется X3DH — тройной обмен ключами с подписями.

Ева (злоумышленница)

Ева перехватывает ключи:

От Алисы → Ева: 49
Ева → Боб: 33 (ключ Евы)

От Боба → Ева: 25
Ева → Алиса: 44 (другой ключ Евы)

Алиса думает, что общается с Бобом,
но ключ (44) от Евы

Боб думает, что общается с Алисой,
но ключ (33) от Евы

Ева вычисляет секрет с Бобом: ?

Ева читает все сообщения.

X3DH — как доказать, что это ты?

У каждого пользователя есть три типа ключей:

  • Identity Key (IK) — долговременный, “паспорт”
  • Signed PreKey (SPK) — меняется периодически и подписан IK
  • One-Time PreKeys (OTPK) — одноразовые, для анонимности

Когда кто-то хочет написать вам, он берёт связку ключей с сервера, проверяет подпись и выполняет несколько DH-обменов — это даёт свойства вроде PFS.

Тип ключа Алиса Боб Назначение
Identity Key (IK) 49 25 "Паспорт" пользователя, долговременный
Signed PreKey (SPK) 48 32 Меняется раз в неделю, подписан IK
One-Time PreKey (OTPK) [17, 23, 41, 53] [19, 29, 37, 43] Одноразовые, для анонимности
Эфемерный ключ 33 44 Одноразовый для каждой сессии

В реальности ключи огромны (2²⁵⁶). Здесь показаны для демонстрации.

Как шифруются сами сообщения (Double Ratchet)

После X3DH у Алисы и Боба есть общий секрет S. Но шифровать им все сообщения нельзя — если ключ украдут, расшифруют всё.

Double Ratchet — постоянная смена ключей: 

Сообщение 1:
Chain Key₁ → Message Key₁ → шифруем "Привет"
            → новый Chain Key₂

Сообщение 2:
Chain Key₂ → Message Key₂ → шифруем "Как дела?"
            → новый Chain Key₃

Если злоумышленник украдет Chain Key₅, он не сможет расшифровать сообщения 1–4 (они уже уничтожены).

Цепочка ключей для сообщений (Алиса → Боб):

Chain Key₀ = 57 (общий секрет)

→ Message Key₁ = 13 → шифруем "Привет"

→ Chain Key₁ = 42

→ Message Key₂ = 28 → шифруем "Как дела?"

→ Chain Key₂ = 17

→ Message Key₃ = 35 → шифруем "Что нового?"

→ ...

Если украдут Chain Key₂ (17), сообщения 1 и 2 уже не расшифровать.

А если пользователь офлайн? (Sealed Sender)

Боб офлайн, Алиса хочет написать. Сервер не должен знать, что это Алиса.

Sealed Sender — скрытый отправитель: 

Вместо:
{ "from": "Алиса", "to": "Боб", "content": "..." }

Алиса отправляет:
{ "to": "Боб", "content": зашифрованный_конверт }

Сервер видит только получателя, но не знает отправителя.

Текущий статус: в Конструкте это always-on Stealth (sealed sender) для подходящего трафика — в production нет пользовательского переключателя. Сертификат отправителя запечатывается identity-ключом получателя; получатель расшифровывает и проверяет, кто написал, сервер — нет. Несколько control-путей (heartbeat’ы, multi-device, session control) по дизайну остаются identified. Stealth не скрывает время отправки, размер сообщения и IP — это видно на транспортном уровне.

Без Sealed Sender:

Сервер видит:

{ "from": "Алиса", "to": "Боб", "content": "[encrypted]" }

С Sealed Sender:

Сервер видит:

{ "to": "Боб", "content": "[sealed]" }

Внутри [sealed]: зашифрованный конверт с отправителем

Как Боб узнает, что ему написали? (Уведомления)

Receipts (подтверждения):

  1. Боб получает сообщение → телефон автоматически отправляет DeliveryReceipt
  2. Боб открывает чат → телефон отправляет ReadReceipt

Даже при Sealed Sender receipts работают: Боб расшифровал сообщение и узнал, что оно от Алисы.

Сколько займёт перебор у злоумышленника?

В этой демке приватные ключи маленькие (1…70), поэтому перебор мгновенный. В реальности безопасность держится на том, что “подобрать ключ” занимает астрономическое время.

Для задачи дискретного логарифма (и в обычном DH, и в ECC) лучшие общие атаки имеют сложность порядка 2^(k/2), где k — “битовая стойкость” группы.

Важно: это грубая оценка “в лоб” для понимания масштаба. Реальные атаки зависят от параметров, реализации, побочных каналов и т.д.

Для DH/ECC обычно уместнее оценка 2^(k/2).

256 бит для ECC — типичный современный уровень.

Почему в реальности используют эллиптические кривые?

Эллиптическая кривая — это множество точек, которые удовлетворяют уравнению вида: 

y² = x³ + ax + b

В криптографии берут не “вещественную” кривую как в школе, а ту же идею, но над конечным полем (всё считается по модулю). Точки образуют группу: есть “сложение точек”, и можно многократно прибавлять одну точку к себе (аналог “умножения”).

Как и в DH, задача для атакующего — восстановить сколько раз прибавляли (дискретный логарифм), и это считается крайне сложным для правильных параметров.

Практический смысл: ECC даёт высокую стойкость при меньших ключах. Поэтому вместо “очень больших чисел” в обычной группе часто используют точки на кривой.

Уровень стойкости ECC RSA/DSA (примерно)
~128-bit 256-bit ECC 3072-bit RSA
~192-bit 384-bit ECC 7680-bit RSA
~256-bit 521-bit ECC 15360-bit RSA

Числа эквивалентности — ориентир “по порядку”, чтобы понять масштаб.

Почему это безопасно?

  1. Даже если сервер взломают — сообщения зашифрованы
  2. Даже если украдут текущий ключ — прошлые сообщения не расшифровать (PFS)
  3. С always-on Stealth (sealed sender) сервер не знает, кто написал eligible-сообщение — только получатель, время и размер
  4. Каждое сообщение шифруется уникальным ключом
